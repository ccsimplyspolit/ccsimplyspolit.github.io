0x01 // Technical Specification & Remediation Patch

### Summary
In `src/core/pipeline_config.rs` and `src/hooks/trust.rs` (`<= v1.0.1`), `rtk` enforces an explicit SHA-256 trust store (`rtk trust`) for repo-local `.rtk/filters.toml` and `.rtk/pipeline.toml` (and blocks `RTK_TRUST_PROJECT_FILTERS=1` outside CI per `CVE-2026-45792`). However, two gaps in `pipeline_config.rs` allow untrusted project configurations or modified directive files to bypass the `rtk trust` gate:

### Root Cause Analysis
1. **Unconditional `RTK_CONFIG_DIR` Override Promotes Untrusted Project `pipeline.toml` to `Scope::User` (`src/core/pipeline_config.rs:82-89, 200-236`)**:
   - In `src/hooks/trust.rs:106-120` (`CVE-2026-45792`), `RTK_TRUST_PROJECT_FILTERS=1` is restricted to verified CI environments so that project-controlled environment files (`.envrc`, `.claude/settings.json`, IDE launch configs) cannot bypass `rtk trust`. Moreover, for `filters.toml`, even the user-global config path is verified via `gated_filter_paths_labeled()` (`src/hooks/trust.rs:208-214`).
   - By contrast, `user_config_root()` in `src/core/pipeline_config.rs:82-89` unconditionally reads `std::env::var("RTK_CONFIG_DIR")` in any environment without a CI check, and `load_from()` (`lines 200-236`) loads `$RTK_CONFIG_DIR/pipeline.toml` and `$RTK_CONFIG_DIR/pipelines/*.toml` with **`Scope::User`** without calling `trust::check_trust_with_content()`.
   - Setting `RTK_CONFIG_DIR=.rtk` (or pointing it at any repo subdirectory) causes `rtk` to load the untrusted repository `pipeline.toml` as `Scope::User`, bypassing `rtk trust` completely and unlocking `Scope::User`-restricted capabilities such as `[proxy.request]` rules and `[upstream.*.api_key_command]` shell execution.
2. **Arbitrary Relative/Absolute Path Traversal and Missing Content Hashing on `directive.def.file` (`src/core/pipeline_config.rs:21-27, 943-950`)**:
   - A project `pipeline.toml` `[directive.<name>]` entry can specify `file = "..."`. `directive_text()` (`lines 21-27`) resolves `directive.origin.parent().unwrap_or(Path::new(".")).join(rel)` and reads the target file with `std::fs::read_to_string(&path)` without checking for `..` traversal or absolute paths, allowing a project directive to inject arbitrary host file contents into the LLM context.
   - Furthermore, `trust::check_trust_with_content()` (`src/core/pipeline_config.rs:248`) only hashes the bytes of `.rtk/pipeline.toml` itself, not the external file referenced by `directive.def.file`, and `trust_summary()` (`lines 943-950`) does not display the referenced file's contents during `rtk trust`. Modifying the external file after `rtk trust` does not invalidate `TrustStatus::Trusted`.

### Impact
- Complete bypass of the `rtk trust` integrity check for `pipeline.toml` when `RTK_CONFIG_DIR` is set in the process environment, elevating repo-local pipeline configs to `Scope::User`.
- Post-approval tampering and arbitrary file inclusion via `directive.def.file` in project `pipeline.toml`.

### Recommended Remediation
1. Restrict `RTK_CONFIG_DIR` overrides or require `RTK_CONFIG_DIR` paths located inside the current project worktree to be treated as `Scope::Project` and verified via `trust::check_trust_with_content`.
2. Confine `directive.def.file` to canonical paths within the `.rtk/` directory and include the referenced file's SHA-256 digest in the `rtk trust` verification record:
