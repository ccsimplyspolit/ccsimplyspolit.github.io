# SAML Temporal Validation Bypass via NaN Timestamp Comparison and Missing SubjectConfirmationData/@NotBefore & Multi-Subject Validation in stytchauth/samlshield

- **CVD ID**: `CVD-2026-SAMLSHIELD-001`
- **Target Program**: HackerOne `twilio` (Paid Bounty Scope `1047285` — `github.com/stytchauth/samlshield`)
- **Repository**: `https://github.com/stytchauth/samlshield`
- **Vulnerable File**: `src/validate.ts (lines 956-1022)`
- **Weakness**: `CWE-290 / CWE-347`
- **Severity**: `High (CVSS 7.7)`

## Summary

I identified a SAML temporal and structural validation bypass in `stytchauth/samlshield` (`src/validate.ts`, lines 956-1022). In `validateTimestamps()`, `new Date(...).getTime()` is evaluated on `Conditions/@NotBefore`, `Conditions/@NotOnOrAfter`, and `SubjectConfirmationData/@NotOnOrAfter` without checking `Number.isNaN(...)`. Because JavaScript comparisons with `NaN` (`now + CLOCK_SKEW_TOLERANCE_MS < NaN` and `now - CLOCK_SKEW_TOLERANCE_MS > NaN`) always evaluate to `false`, any unparseable or non-ISO timestamp string silently bypasses expiration checks. Additionally, `validateTimestamps()` omits checking `SubjectConfirmationData/@NotBefore` and does not enforce a single `<saml:Subject>` element.

## Root Cause Analysis

In `src/validate.ts` (lines 994-1021):
```typescript
if (conditionsNotBefore) {
  const notBeforeTime = new Date(conditionsNotBefore.value).getTime();
  if (now + CLOCK_SKEW_TOLERANCE_MS < notBeforeTime) {
    throw new SAMLAssertionNotYetValidError();
  }
}

if (conditionsNotOnOrAfter) {
  const notOnOrAfterTime = new Date(conditionsNotOnOrAfter.value).getTime();
  if (now - CLOCK_SKEW_TOLERANCE_MS > notOnOrAfterTime) {
    throw new SAMLAssertionExpiredError();
  }
}
```
1. When `new Date(value).getTime()` returns `NaN`, both `<` and `>` comparisons evaluate to `false`, so `validateSAMLResponse()` resolves with `{ valid: true }` instead of throwing.
2. `SubjectConfirmationData/@NotBefore` (SAML 2.0 Core §2.4.1.2) is never checked.
3. Unlike `Response` and `Assertion`, `Subject` is never checked for singleton count or strict-vs-liberal XPath consistency (`//*[local-name()='Subject']`), allowing assertions with multiple `<saml:Subject>` elements if only one contains `SubjectConfirmationData/@NotOnOrAfter`.

- **AFTER PATCH**: `Number.isNaN()` checks, `SubjectConfirmationData/@NotBefore` validation, and singleton `Subject` enforcement reject all three invalid states.

## Impact

Applications relying on `samlshield` as a pre-validation layer before downstream SAML consumption can accept assertions with malformed temporal bounds, future-dated `SubjectConfirmationData/@NotBefore` attributes, or ambiguous multi-`Subject` structures.
